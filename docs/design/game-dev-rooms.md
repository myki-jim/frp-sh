# Game / Dev / LAN：共享房间与场景入口设计

状态：0.5.0 实现与发布验收中。实现采用房主集中发布服务的目录；服务数据走加密 TCP 中继，Game/LAN 保留 P2P。以下历史问题和交互稿记录设计过程，不代表每一项扩展均已包含。

## 0.5.0 已实现

- Game 默认虚拟 LAN，与 LAN 房间互通；`--kind server`、`--tcp`、`--udp` 发布明确服务。缺少创建端口交互输入，脚本立即报错。
- 通用 join 读取房间类型；设备网络需 `--network` 明确授权。新邀请区分 LAN / Dev，自动保存 Profile。
- 多服务目录、独立 TCP 半关闭、多来源 UDP、有界缓冲与并发额度；8 成员 / 64 TCP / 16 UDP 的并发测试通过。
- 房间随机凭据替代邀请中的服务器管理密码；凭据不能跨房间或创建房间。房主可撤销全部邀请并断开活动中继。
- 房主控制文件仅保存于本机用户配置目录；服务目标不上报信令，只上报 ID、名称、协议和建议端口。ID 单调递增，增删服务终止旧会话，重连不重放请求。
- 服务目标、访客监听限制回环地址；公网监听要求密码；TURN 限制为本实例有效 allocation；helper 限制目标、网格检查来源路由，队列与成员数有界。
- 首页提供场景入口、键盘服务表单；服务页显示真实绑定地址，C 复制，I 邀请，G 日志，R 撤销。Profile 通过首页按 2 或 `frp-sh profile` 查看。
- 本地 CLI 验收包含建立、连续三次重连、TCP/UDP、运行中增删服务和撤销；三次本机恢复均约 1 秒。此结果不是跨公网延迟保证。

## 交付边界

本版服务由房主发布，成员选择服务访问。多发布者目录、服务粒度的独立邀请、游戏特定发现适配器和服务模式 P2P 传输属于后续扩展；不在当前命令或页面中展示为已支持。游戏广播发现不能作通用保证。UDP 通过 TCP 中继可能出现有序传输阻塞，要求 UDP 直连的联机使用 Game/LAN。

## 1. 当前问题

- `src/main.rs` 的 game 与 dev 都调用相同的 TCP 转发路径；二者不是不同的网络协议。两端地址、服务和密钥正确时，它们本来可以传送相同类型的 TCP 流量。
- LAN 使用 TUN 传输 IPv4 数据包。TCP 转发以 `CNEW` 开始连接，随后传输长度帧。两者不能直接解码彼此的数据。
- 房间已有 `tun_ip`，但没有正式能力协商。访客选错入口后仍可能显示建链成功，随后报错或反复重连。
- game/dev 的创建地址与加入地址都默认 `127.0.0.1:25565`。这把某一种游戏的惯用端口当成所有游戏和开发服务的默认值。
- `src/tunnel.rs` 在一次连接结束后才接受下一次连接。浏览器并发请求、WebSocket 与 API 同时使用、多玩家长连接都会受到影响。
- `src/p2p/tun.rs` 当前主要做 IPv4 单播路由，没有完整的广播、多播游戏发现机制。不能把“虚拟 IP 可连接”描述成“所有游戏自动出现在局域网列表”。
- 当前邀请只保存 LAN profile，房间界面也总是显示虚拟网络设备卡片。转发房间缺少真实可用的服务入口。

## 2. 产品定义

统一一个房间模型。game、dev、lan 是任务入口和预设，房间声明实际提供的能力。

| 入口 | 默认目标 | 是否需要用户填写端口 | 向朋友展示 |
| --- | --- | --- | --- |
| Game / 局域网联机 | 加入多人虚拟网络，支持游戏自身的 TCP/UDP 通信 | 不需要为隧道指定一个游戏端口；游戏要求直接连接时仍可能需要游戏内显示的端口 | 房主虚拟 IP、游戏提示、真实可用的加入地址 |
| Game / 游戏服务器 | 仅共享明确的游戏服务 | 需要；预设或当前用户可读的本机监听信息可帮助填写，无法确定时询问 | 可复制的 IP:端口，或游戏支持的启动入口 |
| Dev / 开发服务 | 共享本机网站、API、SSH 等指定服务 | 需要端口或 URL；缺失时打开输入页 | 服务名称、协议、本地访问 URL/地址、可用状态 |
| LAN / 设备互通 | 独立虚拟设备网络 | 不需要 | 房间所有设备、虚拟 IP、链路状态 |

Game 局域网与 LAN 使用同一种设备网络能力，可在同一房间互通。Dev 默认申请所选服务的访问能力；需要整机互通时，由用户明确开启设备网络能力。

“互通”意味着同一房间能够发现和使用允许的设备或服务，而不是把 TCP 服务帧交给虚拟网卡解码，也不是因为选择了 dev 就自动共享整台机器。

## 3. Game 流程

### 3.1 创建

首页 → 游戏联机 → 创建房间：

1. 默认选择“局域网联机”。说明：先在游戏里创建世界/开启局域网模式，再邀请朋友。
2. 创建房间并显示房主虚拟 IP、设备卡片、邀请入口。
3. 可选游戏提示卡：记录游戏名称和游戏实际显示的端口，仅帮助生成加入地址，不限制整个虚拟网络只通过该端口。
4. 朋友通过通用邀请加入，自动读取房间能力；不再重复选 game/lan。

选择“游戏服务器”时：

1. 选择游戏预设或“自定义”。每个预设明确 TCP、UDP 或两者，以及可编辑的端口列表。
2. 允许选择当前用户可读取的监听服务；只给出进程、地址、端口和协议等证据，不凭端口猜定游戏身份。
3. 没有输入服务地址/端口时，停留在输入页；不创建空房间、不偷偷使用 25565。
4. 可用性检测失败时说明“服务尚未监听”，允许返回修改或显式选择等待游戏启动。
5. UDP 不使用 TCP 探测成功来声称可用；没有专用探测协议时显示“未验证”，以实际收发数据确认。

### 3.2 加入与发现

- 加入后区分“网络已连接”和“游戏服务可用”。只有实际探测成功才能显示后者。
- 优先提供直接连接地址。游戏支持且已经验证的发现协议，才提供自动发现增强。
- 不承诺所有游戏自动搜索：有的依赖广播、多播、特定网卡、游戏账号匹配或官方服务器。
- 发现增强按游戏协议实现定向转发，限制在授权房间，带去重、速率和跳数限制。不会把物理局域网广播整体搬入房间。
- TUN 是三层 IPv4 设备；需要二层以太网广播的游戏不在首版自动发现承诺内。
- 仅支持官方联网机制而不提供 LAN/私有服务器入口的游戏，需要使用游戏自己的联机方式。

### 3.3 拟议命令

```text
frp-sh game create                         # 默认多人虚拟局域网，不询问隧道目标端口
frp-sh game create --kind server           # 打开游戏服务器配置向导
frp-sh game create --kind server --tcp 25565
frp-sh game create --kind server --udp 19132
frp-sh join 1234                           # 从房间读取实际能力
```

端口数字只是示例，不作为所有游戏的默认值。旧 `game create --service ...` 保留为明确的 TCP 服务共享入口。

## 4. Dev 流程

首页 → 开发协作 → 共享服务：

1. 输入 URL 或端口，如 `http://127.0.0.1:3000`、`127.0.0.1:22`、`3000`。
2. 数字默认指向本机回环地址，类型由用户确认。HTTP/HTTPS/TCP/UDP 是明确的服务类型，不能只通过端口推断。
3. 名称可自动生成并编辑，例如 Web、API、SSH。创建前显示共享目标和访问范围。
4. 房间内可增加多个服务；每个服务独立显示发布者、协议、访问地址、连接数、收发量和可用状态。
5. 访客选择服务后绑定本机回环地址；端口空闲时保持原端口，冲突时允许选择新端口，并更新复制内容。
6. 自动分配端口必须先实际绑定成功，再显示地址；避免检查空闲与绑定之间的竞争。
7. HTTP 服务显示“复制 URL / 打开浏览器”。HTTPS、Host 头和证书域名保持原语义，不能静默关闭证书校验或声称透明代理能解决所有域名依赖。
8. WebSocket/HMR 与普通 HTTP 请求必须可并发。SSH 会话不能堵住其他服务或用户。
9. 本版以私有房间访问为目标；公开互联网 URL 属于另一个显式发布入口，不随分享服务自动开启。

拟议命令：

```text
frp-sh dev create                         # 打开服务输入页
frp-sh dev create --service http://127.0.0.1:3000 --label Web
frp-sh dev add --service 127.0.0.1:8080 --label API
frp-sh join 1234
```

交互式终端缺少必要输入时打开表单。`--plain`、`--json` 或非交互脚本缺少必要输入时返回明确错误和用法，不等待 stdin。

## 5. 房间、协议和邀请

房间元数据需要明确区分用途、授权和传输：

```text
room_id
protocol_version
capabilities: device_network / service_tcp / service_udp / discovery
network_scope: virtual_devices
services[]:
  service_id, publisher_id, label, protocol, suggested_local_port, health
```

- 本地目标地址由发布者保管，访客只能请求已发布的 `service_id`，不能提交任意目标地址让发布者代拨。
- 通用 join 先读取能力，再进入对应页面；game/dev/lan join 是兼容入口，不能盲目决定数据解码方式。
- 请求设备互通会扩大访问范围时，在加入页说明并由用户选择。仅访问开发服务不自动获取设备网络权限。
- 不支持的能力在创建网卡和连接数据面之前明确报错，不进入无限重连。
- 邀请携带房间/能力版本及服务选择提示，实际授权由服务器和发布者检查。旧 v1 邀请继续按其 LAN 语义解析。
- TURN/TCP 是底层连接路径，不能等同于“游戏使用 UDP/TCP”。共享 UDP 服务需要保留报文边界、来源会话映射、超时和大小限制。
- UDP 走可靠有序的 TCP 中继时延迟特性会改变，界面必须如实显示实际路径。
- 多服务数据面使用带类型和 stream/service ID 的帧，支持打开、数据、半关闭、关闭、重置和心跳；每条流有独立流控及有界缓冲。
- 连接重建后重新发布服务和订阅。旧 stream ID 与新会话代次隔离。已经断开的 TCP 会话不会假装恢复，也不会自动重放应用请求。

## 6. 终端页面

```text
首页
  ├─ 游戏联机 → 局域网联机 / 游戏服务器
  ├─ 开发协作 → 新建共享服务 / 最近服务
  ├─ 设备互通
  └─ 加入房间 → 房间号或邀请

房间
  ├─ 设备      可见成员和已授权设备网络
  ├─ 服务      游戏 / Web / API / SSH 等独立卡片
  ├─ 邀请      链接与按平台生成的安装加入命令
  ├─ 日志      保持现有独立日志页
  └─ 设置      设备名、服务管理、访问范围
```

- 同一房间允许多人及多个服务发布者；按设备和服务分别展示。
- `Tab` 切房间页，方向键选卡片，`Enter` 查看/连接，`C` 复制当前可用地址，`I` 邀请，`G` 日志。
- 复制按钮只在有真实有效的访问地址时出现。“网络就绪”“等待游戏启动”“服务拒绝连接”“本地端口占用”是不同状态。
- 设备网络卡片才显示虚拟 IP。纯服务用户不能看到伪造的虚拟网卡“准备中”。
- 默认不共享本地物理局域网。日常会话只使用已经安装的受限网络辅助服务，不重复申请 root/UAC。

## 7. 交付顺序

### 第一批：现有版本的纠错

- 在 join 前用已有 `tun_ip` 检查网络/转发类型，给出明确模式错误，杜绝协议误解码与无效重连。
- 取消 game/dev 的隐式 25565；针对明确端口共享入口补齐交互表单和非交互错误。
- 修正转发房间状态展示和邀请的模式信息。
- 保留旧命令显式参数，不在小版本中悄悄把已有脚本切换成整机网络访问。

### 第二批：共享房间和新入口

- 加入能力协商、通用 join、Game 场景向导和服务目录。
- 实现多玩家、多连接、多服务隔离的转发协议，以及 UDP 服务支持。
- 新数据帧与旧协议有明确版本边界；通过握手协商或清晰升级错误处理，禁止混解码。
- Game 默认局域网语义的切换随新入口版本发布，并同步帮助、profile、邀请和文档。

### 第三批：游戏便利功能

- 有证据的监听服务选择、经过验证的游戏预设、逐项支持的游戏发现适配器。
- 每个适配器记录已验证的游戏版本、平台和连接方式，不以一个“通用游戏加速”开关承诺所有游戏兼容。

## 8. 验收

- Game 局域网房主 + LAN 访客：多人虚拟 IP 的 TCP/UDP 访问可用。
- Game 服务器和 Dev 共享同类服务：所有入口通过通用 join 发现并访问服务，模式不匹配在建链前停止。
- 纯服务访客无法访问未发布端口或任意发布者目标地址。
- 创建服务未填写端口：交互式进入输入页；JSON/脚本快速失败，无默认 25565。
- 8 个用户，每人同时打开多个连接；一个长连接不会阻塞其他用户或服务。
- Dev：并发 HTTP、长时间 WebSocket/HMR 与 SSH 同时可用。
- UDP：保留报文边界，不混淆不同访客来源，超大报文有明确限制。
- 游戏未启动、端口占用、协议不符和无响应分别可诊断，复制的地址与实际绑定一致。
- 断线重连后不会留下旧监听器、旧服务卡片、重复网卡或串到其他会话的流量。
- Windows/macOS/Linux 均用普通账户完成日常操作；邀请、日志、profile 不暴露敏感值。
